# t1-p06: Phase 6: Trino for interactive SQL

## Built
Trino 484 as a second engine on the shared Polaris catalog — no copy of the data. **Query stack**
(`platform/compose.query.yaml`): `trino` (`trinodb/trino:484`, port 8088→8080 since 8080 is the
Spark master UI, catalog conf mounted read-only, `mem_limit: 64g` which the image sizes its heap
from, `lake` network). **Catalog conf** (`platform/conf/trino/catalog/lake.properties`): Iceberg
REST connector pointing at `http://polaris:8181/api/catalog`, warehouse `lake`, OAUTH2 with the
client credentials from the environment (`${ENV:...}` substitution, so no secrets in Git), token
endpoint `/api/catalog/v1/oauth/tokens`, scope `PRINCIPAL_ROLE:ALL`; static S3 keys against
SeaweedFS (`fs.s3.enabled=true` = the native S3 filesystem in Trino 484, path-style access). **Make
target** (`make/query.mk`): `make trino` → `$(DC) exec trino trino --catalog lake`. `query` was
already part of `CORE` in the Makefile, so `make up` now starts Trino with the rest of the core.

## Deviations from the tutorial
What differed, why, and the error that forced it.

1. **`make trino` lives in the new `make/query.mk`, not appended to `make/core.mk`.** Tutorial 0's
   convention is one `.mk` per stack (`storage.mk`, `spark.mk`, `catalog.mk`), carried forward from
   t1-p01/p02/p03 where the same placement note was recorded. No behaviour change; target text is
   the tutorial's verbatim.
2. **Verify harness note (not a repo change):** the SQL checks ran as
   `./dc exec -T trino trino --catalog lake --execute "<query>"` — the exact `make trino` command
   plus `-T`/`--execute`, because the agent shell has no TTY. The target itself was proven with
   piped stdin (`echo "SELECT 1 AS probe" | make trino` → `"1"`), so `make trino` works
   interactively as the tutorial intends.

## Findings
Anything worth remembering: surprises, measurements, ideas for later.

- **No property drift for Trino 484.** The tutorial's warning about `fs.native-s3.enabled` does not
  apply: 484's native S3 filesystem is selected with `fs.s3.enabled=true` (the legacy
  `hive.s3.*`/`fs.hadoop.enabled` path has been removed), and every `s3.*` property the tutorial
  lists exists. Config worked first try.
- **The Polaris guide's extra `Polaris-Realm: POLARIS` header was not needed** with a single realm
  and static S3 keys — same default-realm resolution the Spark client already relies on. Record it
  for the day a second realm exists.
- **Trino is the interactive engine, measurably**: the same gold aggregation ran in 2.5 s wall from
  the CLI (including CLI boot) vs 18.1 s wall from a throwaway `spark-sql` driver container (JVM +
  container boot dominate there; query time itself is a fraction). Note the Spark number is
  start-up-dominated, not engine-dominated.
- `demo.hello` had pre-existing rows this phase didn't create: `(3,'third')` and `(4,'fourth')`,
  each twice (7 rows total before the explore inserts; 9 after). Likely from the owner's notebook
  session against Spark Connect. Harmless in a demo table, but worth knowing when reading old
  verify outputs that expect 2 rows.
- The Trino HTTP API requires an identity for query listings: `X-Trino-User` (or basic auth) on
  `/v1/query`; without it you get `Basic authentication or X-Trino-Original-User or X-Trino-User
  must be sent`. Useful for scripted checks of the UI's query list.
- Trino sees the whole box (`availableProcessors = 112`); heap sized itself from the 64 GiB
  `mem_limit` (~51.2 GiB heap available). Relevant later for Trino tuning and for Phase 7 metrics.
- Trino boot was ~8 s to `SERVER STARTED`; first query ~2.5 s wall.
