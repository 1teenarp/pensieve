# t1-p08: Phase 8: Iceberg table maintenance

## Built
The maintenance job `pipelines/jobs/maintain/optimize_table.py` (`make submit
JOB=maintain/optimize_table.py ARGS="--table <ns.table> [--keep-days N] [--target-mb N]"`): the
tutorial's four procedures in order — `rewrite_data_files` (bin-pack compaction to `--target-mb`,
default 512), `rewrite_manifests`, `expire_snapshots` (`--keep-days` cutoff, `retain_last 5`),
`remove_orphan_files` (same cutoff, with `prefix_listing => true`, see Deviations 2) — plus the
tutorial's learn-by-doing exercises (time travel, rollback, schema evolution, partition evolution,
write-audit-publish branch) and the small-file/compaction/expiry/orphan demonstrations, all run on
the tutorial's own copy `lake.silver.trips_lab`. Written last.

## Deviations from the tutorial
What differed, why, and the error that forced it.

1. **`timezone.utc` kept with `# noqa: UP017` instead of ruff's `datetime.UTC`.** The tutorial's
   `from datetime import datetime, timedelta, timezone` fails pre-commit's ruff 0.17.3 (UP017 —
   ruff now ships a broader default rule set; the repo has no ruff config). Ruff's autofix
   (`from datetime import UTC`) compiles on Python ≥ 3.11 only — the Spark image runs **Python
   3.10** and the job died at import with `ImportError: cannot import name 'UTC' from 'datetime'
   (/usr/lib/python3.10/datetime.py)`. Smallest working fix: the tutorial's `timezone.utc` with
   `# noqa: UP017` and a comment explaining why.
2. **`prefix_listing => true` added to the `remove_orphan_files` CALL.** Without it the procedure
   dies on every table in this lake: `java.io.UncheckedIOException:
   org.apache.hadoop.fs.UnsupportedFileSystemException: No FileSystem for scheme "s3"` —
   `DeleteOrphanFilesSparkAction` lists the table location through **Hadoop's** FileSystem API
   (`FileSystemWalker.listDirRecursivelyWithHadoop`), and Hadoop has no driver for the `s3://`
   scheme our tables use (Iceberg reads them via the S3FileIO/AWS SDK, bypassing Hadoop). The
   procedure's `prefix_listing` option switches to the FileIO path
   (`FileSystemWalker.listDirRecursivelyWithFileIO`), which `S3FileIO` supports
   (`SupportsPrefixOperations`). Verified: the run that crashed at step 4 twice completes with
   exit 0.
3. **The tutorial's "count should drop" verify outcome is impossible on `silver.trips` as it
   stands** — not an error, a table-state fact: the current snapshot has exactly 1 file per day
   partition (182 files), `rewrite_data_files` bin-packs **within** partitions only (default
   `min-input-files` 5), so there is nothing to merge — 0 files rewritten, count and avg
   unchanged. The verify's intent (compaction visibly merges small files) is demonstrated on the
   tutorial's own copy (`lake.silver.trips_lab`) after creating the small-file problem the
   tutorial's Explore 1 prescribes (500 single-row inserts): 548 → 17 files, 0.55 MB → 17.57 MB
   avg. For the real table the fix is partition design (day → month or bucket), not compaction.
4. **Expiry was demonstrated with `--keep-days -1` on the lab copy only.** The default
   `--keep-days 7` cannot free anything yet (every snapshot is < 7 days old); a negative offset is
   the only way through the job's interface to make expiry visibly delete files. Side effect
   recorded: step 4 then correctly aborts on the ≥24 h guard (exit 2, steps 1–3 already committed).

## Findings
Anything worth remembering: surprises, measurements, ideas for later.

- **A crashed job run still commits what succeeded before the crash.** Run 2 crashed at
  `remove_orphan_files` but its `rewrite_manifests` had already committed (7 manifests → 1 ×
  32.6 KB). Each procedure commits independently; reruns are safe (later runs are no-ops) — which
  is also what makes the tutorial's ordering claim work in practice.
- **The `Failed to load catalog: silver` WARN with a full `CATALOG_NOT_FOUND` stack appears once
  per procedure per run and is harmless.** Iceberg's `Spark3Util.catalogAndIdentifier` tries the
  first name part as a catalog, catches the failure, logs the WARN and falls back to the session's
  current catalog (`lake`) with `silver.trips` as namespace+table. The tutorial's 2-part
  `--table silver.trips` form works as-is on Iceberg 1.11; only the log noise suggests otherwise.
- **CTAS does not inherit the partition spec.** `CREATE TABLE trips_lab AS SELECT * FROM
  silver.trips` produced an unpartitioned copy of a `days(pickup_ts)` table. Anything that copies
  tables by CTAS in later phases must restate `PARTITIONED BY` explicitly.
- **`rewrite_data_files` converts old-spec files into the current spec.** The 46 unpartitioned
  files were rewritten into `bucket(16, pu_zone_id)` files, re-partitioned by row hash (buckets
  4.7–23.8 MB). Maintenance is also how mixed-spec tables converge — and a re-partitioning tool.
- **The WAP "main is unchanged" check is untrustworthy inside the same session.** After
  `VERSION AS OF 'audit'`, the plain-name `SELECT count(*)` returned the **branch's** count
  (19,732,739) while main was verifiably at 19,732,738 — the session's cached table instance is
  keyed by identifier, not by ref. Check from a fresh session (or another engine) after any
  branch time-travel query.
- **`rollback_to_snapshot` on the REST catalog is a pointer move**: `main` pointed directly back
  at the CTAS snapshot; no new snapshot was created and the superseded delete snapshot simply
  became unreferenced (its files were freed by the later expiry).
- **The ≥24 h guard on `remove_orphan_files`** (`Cannot remove orphan files with an interval less
  than 24 hours`) means the job's `--keep-days` must be ≥ 1 for step 4 to run; `--keep-days 0`
  and negative values abort the job after expiry has already committed.
- **Bucket partition fields carry the width in their name**: `bucket(16, pu_zone_id)` →
  `pu_zone_id_bucket_16`.
- **Real-table backlog (silver.trips)**: ~1.16 GB of superseded files (958 objects vs ~380
  needed) stays pinned until the 7-day cutoff passes on 2026-11-08; the 182 × 1.65 MB day
  partitions are themselves the small-file problem, but the fix is partition evolution (month or
  bucket), which compaction cannot do — a Phase 10 hardening candidate, alongside the
  `rest.auth.type=oauth2` inference warning noted in t1-p07.
- Timings: job runs 18–53 s wall each (container + JVM boot ~10–15 s dominate); 500 INSERT commits
  153 s; the compaction of 548 files → 17 took ~20 s of the 53 s run.
- Harness notes (not repo changes): `spark-sql -f` inside the `spark-client` container is the
  workhorse for multi-statement sessions (`./dc run -T --rm -v /tmp/opencode/sql:/sql:ro
  spark-client sh -c 'spark-sql --conf spark.driver.host=$(hostname -i) -f /sql/<file>.sql'`);
  `./dc run` options (`-v`) must precede the service name; many-commit loops are fastest through
  `spark-submit` of a small driver script.
