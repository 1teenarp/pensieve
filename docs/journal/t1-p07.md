# t1-p07: Phase 7: Observability and tuning

## Built
Spark metrics into the existing Prometheus/Grafana stack, tuning defaults for this box, and the
NUMA-pinned worker shape. `platform/conf/spark/metrics.properties` (committed — no variables)
turns on Spark's PrometheusServlet everywhere: `/metrics/prometheus` for workers and drivers,
`/metrics/master/prometheus` and `/metrics/applications/prometheus` on the master. The defaults
template gains `spark.ui.prometheus.enabled`, `spark.metrics.appStatusSource.enabled`,
`spark.io.compression.codec zstd`, and the tuning entries (`spark.executor.memoryOverhead`,
`spark.sql.shuffle.partitions` per shape, `advisoryPartitionSizeInBytes 128m`,
`files.maxPartitionBytes 256m`). Shapes: `small.env`/`large.env` gain `EXECUTOR_MEMORY_OVERHEAD`
and `SPARK_SHUFFLE_PARTITIONS`; new `shapes/numa.env` (`SPARK_WORKERS=0`, 4 × 20 cores / 160g =
the tutorial's "about 80 of 112 threads, 640 GB"). `scripts/gen_numa_workers.py` generates the
gitignored `platform/compose.numa.yaml` — one worker per node via `extends` + `numactl
--cpunodebind --membind` + `cap_add: [SYS_NICE]`, ports 8101–8104; `make/spark.mk` gains
`up-numa` and `down-numa` and renders the two new conf variables. `docs/benchmarks.md` gets the
executor-granularity A/B the Verify asks for. The Grafana side lives in the owner's
observability-stack, so this PR carries prepared artifacts: the exact Alloy scrape blocks
(validated and end-to-end-tested against a throwaway Prometheus) and the six-panel dashboard
`platform/conf/grafana/spark-lakehouse.json` in the owner's dashboard conventions, to be copied
into `observability-stack/server/grafana/dashboards/`.

## Deviations from the tutorial
What differed, why, and the error that forced it.

1. **`shapes/numa.env` uses `EXECUTOR_MEMORY=34g` + 6g overhead, not the tutorial's 40g + 6g.**
   The tutorial's own numbers don't pack: 4 executors × (40g + 6g) = 184g > the 160g worker it
   specifies, so only 3 executors per worker would fit and 5 of every 20 cores would idle.
   34g + 6g = 40g × 4 = exactly 160g — all 80 cores of the tutorial's "about 80 of 112 threads"
   are reachable. Verified live: 16 executors of 20.2 GiB (34g heap) ran the gold rebuild.
2. **`down-numa` target added (tutorial has none).** `./dc --profile numa down` with only the
   numa file fails validation: `service "spark-worker-n3" depends on undefined service
   "spark-master"` — the base worker's `depends_on` is inherited through `extends`, so the numa
   file alone is not a valid project. `make down-numa` removes just the n-services with
   `rm -sf`; without it, `make up` after `up-numa` leaves 6 registered workers (observed:
   96 cores in the master UI).
3. **The "disk spill per minute" panel became "Executor disk used (GB)".** Spark 4.1's metric
   servlets expose no live disk-spill series — the executor heartbeat set was enumerated
   (`metrics_executor_*`: memory/GC/shuffle/diskUsed, no `diskBytesSpilled`) and the driver's
   appStatus source has only job/stage/task counters. The panel tracks block-manager disk use
   instead; its description says where true spill is visible (app UI / history server).
4. **The Alloy scrape blocks and Grafana dashboard live in the owner's observability-stack, not
   this repo** — the pensieve side publishes the endpoints, and the scrape/dashboard belong to
   the owner's client (on this box) and server (on `metrics`). Owner approved the split: this PR
   carries the exact blocks (validated + e2e-tested) and the dashboard JSON as hand-off
   artifacts (`platform/conf/grafana/spark-lakehouse.json`).
5. **Alloy's Docker discovery label is `__meta_docker_port_public`, not Prometheus's
   `__meta_docker_container_port_public`.** The first e2e attempt produced zero worker series:
   the non-existent label made the address rewrite fail silently and Alloy dialled the workers'
   container IPs (unreachable from the client network). Found by introspecting the running test
   Alloy's component exports via its GraphQL API. The e2e test is exactly what caught this
   before the owner pasted a broken block.
6. **Conf changes need explicit recreation.** `make up` after rendering new conf recreated
   nothing (bind-mount content is not part of compose's recreation decision); master, workers,
   history and connect were force-recreated (`spark-connect` last, after confirming its session
   was idle). Recorded as a finding too — any future `spark-defaults.conf` change needs the same
   treatment.
7. **Metric paths use the trailing slash.** `/metrics/master/prometheus` answers 302 →
   `…/prometheus/`; the scrape blocks use the slash form directly.
8. **Small/large shapes gained `EXECUTOR_MEMORY_OVERHEAD=3g` and `SPARK_SHUFFLE_PARTITIONS`
   40/120** (the tutorial's tuning table's 2–3×-cores rule at each shape's app cap). Without an
   overhead, `large.env` would pack 3 × 33g = 99g against the 100g worker limit only by luck;
   3g keeps the packing explicit and unchanged.
9. **`gen_numa_workers.py` differs from the tutorial's listing in two ruff-driven ways**: the
   file carries the executable bit (ruff EXE001 — a shebang without it fails pre-commit) and
   writes through a context manager (ruff SIM115 — `open(...).write(...)` on one line fails).
   Same behaviour as the tutorial's code.

## Findings
Anything worth remembering: surprises, measurements, ideas for later.

- **Series naming** (from the live endpoints): master `metrics_master_{workers,aliveWorkers,apps,
  waitingApps}`; workers `metrics_worker_{coresUsed,coresFree,memUsed_MB,memFree_MB,executors}`;
  executor heartbeats `metrics_executor_{memoryUsed_bytes,maxMemory_bytes,diskUsed_bytes,
  totalShuffleWrite_bytes_total,totalShuffleRead_bytes_total,totalDuration_seconds_total,
  totalGCTime_seconds_total,activeTasks,…}`. Gauges render twice (`_Number` and `_Value` with
  `type="gauges"`); dashboards use `_Value`. **The master has no core gauges in 4.1** — the
  cores panel is built from worker series.
- **Executor heartbeats only cover the Connect server's executors** (its own driver serves
  `/metrics/executors/prometheus`). Batch-job executors belong to throwaway driver containers
  whose UI ports are never published — their internals are only visible in the app UI/history
  server. A future idea: publish the batch driver's 4040 in `make submit` (`--publish`) so batch
  executor metrics are scrapable too.
- **Worker host ports are reassigned on every recreate** (observed 8081/8082 → 8083/8084 → 8091
  across recreations) — Docker picks from the published range. The docker-SD worker discovery in
  the Alloy blocks is load-bearing, not cosmetic.
- The Connect driver serves `/metrics/executors/prometheus` even without `spark.ui.prometheus
  .enabled` (Spark Connect default), but `/metrics/prometheus` (driver + appStatus) appeared
  only after the conf change.
- **appStatus series embed the app id in the metric name** (`metrics_app_<id>_driver_appStatus_…`)
  — they churn on every app restart, so the dashboard avoids them; executor heartbeat series use
  labels instead.
- The GC share on real work is ~1% at 20–46 g heaps; the panel's 10% red threshold is where it
  would start to matter.
- Benchmark: 8-core executors cut Σ task time ~15% vs 4-core executors at equal total cores;
  wall is submit-floor-bound (~10 s container + JVM boot) at this data size. No spill anywhere —
  the scratch panel matters only for much bigger shuffles.
- Pre-existing noise while jobs run: Iceberg's `rest.auth.type=oauth2` inference warning and the
  `oauth2-server-uri` fallback warning (github.com/apache/iceberg/issues/10537) — harmless, from
  the tutorial-era conf; a Phase 10 hardening candidate.
- Harness note (not a repo change): for quick Connect probes, use the jupyter container
  (`./dc exec jupyter python3 …`) — the spark-client image's plain `python3` has neither pyspark
  on `PYTHONPATH` (our Dockerfile's `PYTHONPATH=/opt/libs` overrides the base image's
  `/opt/spark/python/lib/...`) nor `grpcio`; a Connect session needs the full client, which only
  the jupyter image carries.
- **`pre-commit run --all-files` misses untracked files** (it uses `git ls-files`), so new files
  only meet ruff at the commit hook — twice this phase the commit hook caught what the
  --all-files gate had passed (the untracked generator script). Stage new files before trusting
  an all-files green.
- The `.env` Polaris/S3 secrets in the rendered conf remain `change-me` placeholders (as since
  t0); nothing new exposed by the metrics work.

### The exact Alloy blocks (validated, e2e-tested)

```alloy
// ---------------------------------------------------------------------------
// Spark lakehouse (pensieve) — master, workers, Spark Connect driver.
// The pensieve stack publishes these ports on the host: master UI 8080,
// worker UIs one Docker-assigned host port each (from the 8081-8096 range,
// or 8101-8104 for the NUMA shape), Spark Connect driver 4040. Worker
// targets come from the Docker API so the scrape follows the cluster's
// shape and survives container recreation (host ports are reassigned).
// ---------------------------------------------------------------------------

prometheus.scrape "spark_master" {
  targets = [
    {
      __address__ = "host.docker.internal:8080",
      job         = "spark-master",
    },
  ]
  metrics_path = "/metrics/master/prometheus/"
  forward_to = [prometheus.remote_write.server.receiver]
}

prometheus.scrape "spark_applications" {
  targets = [
    {
      __address__ = "host.docker.internal:8080",
      job         = "spark-applications",
    },
  ]
  metrics_path = "/metrics/applications/prometheus/"
  forward_to = [prometheus.remote_write.server.receiver]
}

prometheus.scrape "spark_workers" {
  targets      = discovery.relabel.spark_workers.output
  metrics_path = "/metrics/prometheus/"
  forward_to   = [prometheus.remote_write.server.receiver]
}

prometheus.scrape "spark_connect" {
  targets = [
    {
      __address__ = "host.docker.internal:4040",
      job         = "spark-connect",
    },
  ]
  metrics_path = "/metrics/executors/prometheus/"
  forward_to = [prometheus.remote_write.server.receiver]
}

discovery.relabel "spark_workers" {
  targets = discovery.docker.containers.targets

  // only the lakehouse Spark worker containers
  rule {
    source_labels = ["__meta_docker_container_name"]
    regex         = "/homelab-spark-worker.*"
    action        = "keep"
  }

  rule {
    source_labels = ["__meta_docker_container_name"]
    regex         = "/(.*)"
    target_label  = "container"
  }

  rule {
    target_label = "job"
    replacement  = "spark-worker"
  }

  rule {
    source_labels = ["__meta_docker_port_public"]
    regex         = "(\\d+)"
    target_label  = "__address__"
    replacement   = "host.docker.internal:${1}"
  }
}
```

(Append at the end of `client/alloy/config.alloy`, after the existing blocks; it reuses the file's
`discovery.docker "containers"` and `prometheus.remote_write "server"`.)
