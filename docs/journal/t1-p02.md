# t1-p02: Phase 2: A Spark standalone cluster in Docker

## Built
A Spark standalone cluster from one custom image, sized by the shape file. `platform/docker/spark/`
holds the Dockerfile (base `spark:4.1.2-scala2.13-java17-python3-ubuntu`; bakes the Iceberg 1.11.0
runtime, the Iceberg AWS bundle and the Postgres JDBC 42.7.7 jar so jobs never download at runtime;
installs the locked Python packages; adds the `lake-submit` wrapper that advertises the driver's
container IP), `requirements.in` → committed `requirements.lock` (via `make lock`, uv) and
`python-version` (3.10, read from the base image). `platform/conf/spark/spark-defaults.conf.template`
renders per shape into gitignored `spark-defaults.conf`. New `make/spark.mk`: the `conf` render
(pluggable per-stack pattern from t1-p01), `submit` and the `sql` placeholder. New
`platform/compose.spark.yaml`: master (UI :8080), workers scaled by `--scale spark-worker=$(SPARK_WORKERS)`
(host ports 8081–8096, Docker `cpus`/`mem_limit` ~15% above Spark's own limits, scratch mount,
worker cleanup opts), history server (:18080), and a throwaway `spark-client` under the `tools`
profile. `shapes/large.env` (4 workers × 12 cores / 100g) added for the resize verify. `make up`
now builds the image and starts the whole stack; the `SCALE` guard added in t1-p01 needed no change.

## Deviations from the tutorial
What differed, why, and the error that forced it.

1. **Target placement (carried forward from t1-p01).** The tutorial says "add these targets to
   `make/core.mk`"; per tutorial 0's convention ("Make targets live in `make/<stack>.mk`"), the
   `conf` render, `submit` and `sql` live in the new `make/spark.mk`. No behaviour change. The
   `sql` target keeps the tutorial's known-placeholder form (host-side `hostname -i`); Phase 3
   replaces it with the container-side version.
2. **Inline comment after `COPY` removed.** The tutorial's Dockerfile line
   `COPY requirements.lock /tmp/requirements.lock      # requirements.in: pyarrow, pandas, requests`
   would fail: Docker only treats `#` comments at line start, so BuildKit would try to copy a file
   named `#…`. The comment moved to its own line above the `COPY`.
3. **Shape-switch staleness guard in `spark.mk`.** Make tracks file mtimes, not variables, so
   rendering with `SHAPE=large` and then running `make up` (SHAPE back to default small) would
   leave the large values in `spark-defaults.conf` (small.env is older than the render → no
   re-render) — workers would scale to 2×8 cores while the conf still asks for 30g executors and a
   48-core cap. The rendered file now records its shape in a stamp file
   (`spark-defaults.conf.shape`, gitignored); on mismatch the target is marked phony, forcing
   exactly one re-render. Same shape → idempotent ("Nothing to be done"), preserving the property
   the owner required for `conf` in the t1-p01 review. Verified in both directions during the
   large→small resize.
4. **`python-version` = 3.10** — read from the pulled base image (3.10.12), not guessed.
5. **`build:` moved from the shared anchor to `spark-master` only, with `provenance: false`.**
   Forced by real behaviour: with the tutorial's `build:` in the `x-spark` anchor, compose v5.6.1
   stamps every service's built image with `com.docker.compose.service` (verified: building each
   service separately yields three different image IDs — `5c04c18a…` master, `50920e44…` worker,
   `e3eab288…` history), so three services sharing the tag `lakehouse/spark:4.1.2` race to export
   it. The tag ended up on whichever target finished last, so the image digest churned between
   builds and `make up` **intermittently recreated all Spark containers** (observed: recreates on
   some runs, no-op on others) — a `make up` could kill running jobs. One build target = one
   writer to the tag: 3 consecutive `make up` runs → 0 recreates, tag digest stable
   (`5c04c18a…`). `provenance: false` additionally keeps cache-hit rebuilds digest-stable
   (attestation payloads otherwise vary per build). The other services resolve the tag locally at
   create time (tested by untagging: `up -d --build` rebuilds once and starts everything, no pull
   attempted).

## Findings
Anything worth remembering: surprises, measurements, ideas for later.

- `uv` and `pre-commit` live at `~/.local/bin/` and are **not on the PATH of non-login shells** —
  prefix `PATH="$HOME/.local/bin:$PATH"` when an agent runs `make lock` or `pre-commit`.
- Host prep for this phase was already done in t0: `spark-events` and scratch dirs are uid 185,
  matching the image's `spark` user — no permission work was needed at `make up`.
- **Compose v5.6.1 stamps built images with `com.docker.compose.service`** (and project) labels —
  never let several services share one `image:` tag while each has `build:`. Recorded in full
  under Deviations 5.
- BuildKit warns `InvalidDefaultArgInFrom` for `ARG SPARK_BASE` on every build — expected (the
  base comes from compose build args) and harmless.
- pip install succeeded **without** the `--break-system-packages` fallback (Ubuntu 22.04 ships pip
  22.0.2, pre-PEP 668 enforcement); the fallback stays in the Dockerfile for future base bumps.
- SparkPi on the small shape: ~7–8 s wall clock (job 6.4 s / 7.7 s across two runs) including
  driver startup.
- Event logs live on the mount, so the history server keeps showing runs across master/container
  recreations — state belongs to `/lake/lakehouse/spark-events`, not the containers.
- **Iceberg 1.12.0 exists** (Maven metadata, released 2026-09-30); `versions.env` pins 1.11.0 per
  the tutorial. Phase 3's troubleshooting mentions the 1.11.0 `FormatModelRegistry` read issue —
  if it bites, 1.12.0 is the "newer patch" candidate (needs a `versions.env` change + journal note).
- `PG_JDBC_VERSION=42.7.7` is hardcoded as an ARG in the Dockerfile (as the tutorial wrote it) —
  it exists on Maven. Candidate to move to `versions.env` for consistency if the owner wants.
