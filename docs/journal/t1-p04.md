# t1-p04: Phase 4: Submitting jobs and working interactively

## Built
Two ways into the cluster. **Batch**: `libs/pensieve/lake/spark.py` (`get_spark(app_name)` — one
session per job; cluster, catalog and S3 settings come from `spark-defaults.conf`) and the first
job `pipelines/jobs/demo/row_count.py`, run through the existing `make submit` (throwaway
`spark-client` driver container from t1-p02) with per-job sizing via `SUBMIT_OPTS`. **Interactive**:
a `spark-connect` service in `platform/compose.spark.yaml` (long-running driver,
`start-connect-server.sh`, gRPC :15002, driver UI :4040, `spark.driver.host=spark-connect`,
dynamic allocation with shuffle tracking and `executorIdleTimeout=120s`, capped by
`CONNECT_MAX_CORES`), plus the `notebook` stack: `platform/compose.notebook.yaml` and
`platform/docker/jupyter/` (`quay.io/jupyter/minimal-notebook:2026-10-28` +
`pyspark-client==4.1.2` from a committed 14-package lockfile, built as
`lakehouse/jupyter:2026-10-28`, repo `notebooks/` mounted at `/home/jovyan/work`). The tutorial's
notebook cells are committed as `notebooks/demo/spark-connect.ipynb` so the interactive verify is
reproducible headlessly. `CONNECT_MAX_CORES` added to `shapes/small.env` (16) and
`shapes/large.env` (48).

### Explore (first bullet): where does the code run?

In the notebook container against `sc://spark-connect:15002`: `pyspark.__file__` →
`/opt/conda/lib/python3.13/site-packages/pyspark/__init__.py` (the notebook's own Python, no JVM);
`spark.sparkContext` raises `PySparkAttributeError: [JVM_ATTRIBUTE_NOT_SUPPORTED] Attribute
'sparkContext' is not supported in Spark Connect as it depends on the JVM` — the notebook sends a
plan and the server's driver runs it. That's the whole design.

## Deviations from the tutorial
What differed, why, and the error that forced it.

1. **The row count prints 6, not the tutorial's 2.** Not a code problem: the owner manually
   inserted 4 test rows after t1-p03 (`3 third` ×2, `4 fourth` ×2 — confirmed by the row-level
   SELECT above). The job's count is correct for the current table state; the tutorial's `2`
   assumed the t1-p03 state.
2. **`import argparse, sys` split into two imports.** Ruff's default selected rules include E401
   (multiple imports on one line), which fails the tutorial's form. No behaviour change.
3. **`CONNECT_MAX_CORES` defined in the shape files** (`small.env`: 16, `large.env`: 48). The
   tutorial only shows the compose fallback `${CONNECT_MAX_CORES:-16}` and never says where the
   variable lives. Sized it to `APP_MAX_CORES` in each shape — same semantics (how much of the
   cluster one application may take); the `:-16` fallback stays in compose.
4. **`image: lakehouse/jupyter:${JUPYTER_TAG}` added next to `build:`.** The tutorial's
   `compose.notebook.yaml` omits it, so compose auto-tags the built image `homelab-jupyter:latest`
   — the working agreement forbids `latest` tags, and t1-p02 established the explicit-tag-next-to-
   build discipline. Same image (3.01 GB), stable name; the stale `homelab-jupyter:latest` was
   removed locally after the rebuild.
5. **Interactive verify ran headlessly.** The agent has no browser: the notebook was executed with
   `jupyter nbconvert --to notebook --execute` inside the container and the cell outputs checked
   (namespace table + 6-row pandas frame, shown above). The browser path (`http://pensive:8890`
   with the token from `./dc logs jupyter`) is left for the owner to eyeball. Committing
   `notebooks/demo/spark-connect.ipynb` (the tutorial's exact cells) is what makes this
   reproducible; nbstripout keeps it output-free.

## Findings
Anything worth remembering: surprises, measurements, ideas for later.

- **pyspark-client is sdist-only on PyPI** (no wheel for 4.1.2). pip builds it during the image
  build fine, and the client package keeps the notebook image lean (3.01 GB total: 2.49 GB base +
  ~0.5 GB of client deps) versus pulling the full ~317 MB pyspark distribution.
- **The notebook stack runs newer client libs than the Spark image** (pandas 3.1.0 / pyarrow
  26.0.0 / numpy 2.5.4 vs the Spark image's pandas 2.3.3 / pyarrow 25.0.1). Irrelevant for
  correctness: with Connect the notebook is a pure client and results arrive as Arrow batches —
  the client↔server contract is the Connect protocol, not the library versions.
- **The Connect server inherits everything from the mounted `spark-defaults.conf`** (master URI,
  Iceberg REST catalog, S3 keys, event logging); only Connect-specific confs sit on the command
  line. Notebooks see `lake` as the default catalog with zero extra setup — `spark.sql.defaultCatalog=lake` carried straight through.
- **Dynamic allocation + shuffle tracking works on the standalone cluster**: the server starts
  with 0 executors, grants one (shape-default 4c/20g) on the first query, and `executorIdleTimeout=120s` gives it back. No external shuffle service needed.
- **Master UI quirk**: `GET /api/v1/applications` returns the HTML page even with
  `Accept: application/json` in this setup, so scripted checks can't use the master's JSON API;
  the front page embeds the app table directly (parsed it to confirm app states). The history
  server (:18080) has a working JSON API — use that for scripted checks in later phases.
- The tutorial's sized-submit example (`spark.cores.max=32`) on the small shape (16 total cores)
  simply runs with the 16 available cores — Spark takes what exists rather than hanging; the
  EMR mapping (cluster shape vs per-step settings) matches what we saw.
- Timings: batch job app duration 6 s (master UI) for a metadata-only count; whole `make submit`
  wall time dominated by container start + JVM boot (~30 s).
