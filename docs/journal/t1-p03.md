# t1-p03: Phase 3: An Iceberg REST catalog with Apache Polaris

## Built
Polaris 1.8.0 on Postgres 17 as the Iceberg REST catalog: `platform/compose.catalog.yaml` adds the
`catalog` stack — `catalog-db` (Postgres, healthcheck-gated, data in `${PG_ROOT}/catalog-db`, init
script creating the Polaris schema), `polaris` (REST API :8181, health :8182, reads S3 with static
keys, dev-only `POLARIS_READINESS_IGNORE_SEVERE_ISSUES` flagged for Phase 10) and a one-time
`polaris-bootstrap` under the `setup` profile. `scripts/create-catalog.sh` creates the `lake`
INTERNAL catalog (`s3://warehouse/lake`, path-style, `stsUnavailable` so engines use static keys)
and grants `CATALOG_MANAGE_CONTENT` to the `service_admin` principal role via `catalog_admin`.
New `make/catalog.mk` (`catalog-bootstrap`, `catalog-create` with the health-poll loop) and the
`sql` target in `make/spark.mk` now reads the driver IP inside the container (the Phase 2
placeholder replaced). `spark-defaults.conf.template` gained the Iceberg REST catalog block
(extensions, `lake` catalog via `SparkCatalog`/rest/S3FileIO, S3 endpoint + keys, region); the
`envsubst` list in `spark.mk` grew the four new variables. Catalog name `lake` verified end to end:
Spark created `lake.demo.hello`, wrote Parquet + Iceberg metadata to SeaweedFS, and read it back.

### Explore: how little a catalog holds

`./dc exec catalog-db psql -U polaris -d polaris`: `polaris_schema` has 8 tables (`entities`,
`grant_records`, `events`, `version`, …). The `entities` row for `demo.hello` (type_code 7,
id `8357742806700994125`) carries `internal_properties.metadata-location =
s3://warehouse/lake/demo/hello/metadata/00001-892f3f05-….metadata.json` — the pointer is the
catalog's real content; current-snapshot-id `2002020361916107115` matches what Spark returned,
and everything else (2 Parquet files, 2 metadata.json, manifest + manifest-list Avro) is only in
SeaweedFS.

## Deviations from the tutorial
What differed, why, and the error that forced it.

1. **The catalog database needs its schema created before bootstrap; the tutorial's compose omits
   this.** First `make catalog-bootstrap` failed: `RuntimeException: Error executing sql script:
   Failed due to 'ERROR: no schema has been selected to create in'` (PSQLException inside
   Polaris's `DatasourceOperations.executeScript`). Polaris 1.8.0 connects with
   `currentSchema=POLARIS_SCHEMA` (shipped default; folded by Postgres to `polaris_schema`) and its
   docs state the schema "must exist before Polaris connects: Polaris does not issue
   `CREATE SCHEMA`". Verified the DB only had `public` before the fix. Fix: new
   `platform/conf/catalog-db/01-schema.sql` (`CREATE SCHEMA IF NOT EXISTS POLARIS_SCHEMA;`) mounted
   at `/docker-entrypoint-initdb.d` (the same pattern the tutorial itself uses for `source-db` in
   Phase 5) for fresh volumes, plus a one-shot
   `./dc exec -T catalog-db psql -U polaris -d polaris -c 'CREATE SCHEMA IF NOT EXISTS
   POLARIS_SCHEMA;'` for the volume this phase had already initialized (init scripts only run on
   first init). Non-destructive; no data touched.
2. **Target placement (carried forward from t1-p01/p02).** The tutorial says "extend
   `make/core.mk`"; per tutorial 0's convention ("Make targets live in `make/<stack>.mk`"),
   `catalog-bootstrap`/`catalog-create` live in the new `make/catalog.mk`, and the `sql` fix went
   into `make/spark.mk`, where the target already lives. No behaviour change.
3. **`envsubst` variable list extended in `spark.mk`.** The tutorial appends
   `${POLARIS_CLIENT_ID}`, `${POLARIS_CLIENT_SECRET}`, `${S3_ACCESS_KEY}`, `${S3_SECRET_KEY}` to
   the template but never says to update the render. The per-stack render uses an explicit
   envsubst list (property established in the t1-p01 review), so the four variables were added;
   without them the rendered conf would keep the literal `${…}` strings and Spark would fail to
   authenticate.
4. **Verify harness note (not a repo change):** the SQL verify ran through the exact `make sql`
   command with `docker compose run -T` so output could be captured non-interactively; the target
   itself was additionally proven interactively under a TTY (`SHOW NAMESPACES IN lake` → `demo`).

## Findings
Anything worth remembering: surprises, measurements, ideas for later.

- **The Iceberg 1.11.0 `FormatModelRegistry` read issue did not bite** (tutorial troubleshooting
  item): reads of `lake.demo.hello` and the `snapshots` metadata table worked with
  `iceberg-spark-runtime-4.1_2.13-1.11.0.jar`. Keep 1.12.0 in mind only if a future write path
  hits it.
- **Two Iceberg REST client warnings in Spark worth a follow-up** (warnings today, removals
  tomorrow): (a) `credential` set without `rest.auth.type` → inferred `oauth2`; (b) no
  `oauth2-server-uri` → client defaults to
  `http://polaris:8181/api/catalog/v1/oauth/tokens`, "this automatic fallback will be removed in a
  future Iceberg release" (apache/iceberg#10537). Adding
  `spark.sql.catalog.lake.rest.auth.type=oauth2` and
  `spark.sql.catalog.lake.oauth2-server-uri http://polaris:8181/api/catalog/v1/oauth/tokens` would
  silence both; not done here because the tutorial doesn't include them (record for a
  hardening/upgrade phase).
- Polaris 1.8.0 stores its state in schema `polaris_schema` (8 tables); the `entities` row for a
  table holds the metadata-location pointer plus cached summary fields — this is the whole "tiny
  catalog" story, demonstrated with real output above.
- `docker compose run` auto-enables the target service's profile, so `make catalog-bootstrap`
  reaches the `setup`-profiled `polaris-bootstrap` without `--profile setup`; the healthy-gated
  `depends_on` starts `catalog-db` automatically.
- Postgres 17 on a root-owned pre-created parent dir needs no host prep: the image entrypoint runs
  as root and chowns its own data dir (`${PG_ROOT}/catalog-db`).
- Timings on the small shape (16-core cap): namespace/table create ~1 s each, 2-row INSERT ~4 s
  (commit + metadata write dominate at this size), SELECT ~2.5 s.
- Re-ran `make up` after adding the stack: 0 recreates — the image-tag discipline from t1-p02
  carries over (no `build:` in this stack, published images only).
