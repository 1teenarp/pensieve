# t1-p01: Phase 1: S3-compatible object storage (SeaweedFS)

## Built
A SeaweedFS S3 endpoint on the `lake` network at `http://seaweedfs:8333`, running 4.51 in `mini`
mode (master + volume + filer + S3 gateway in one process), with `warehouse` and `landing`
buckets. Files: `platform/compose.storage.yaml`, `platform/conf/seaweedfs/s3.json.template`
(rendered to `s3.json`, gitignored), and the make targets `buckets` and `s3` in the new
`make/storage.mk`. Config rendering is pluggable per stack (owner review fix): `conf` is a
recipe-less aggregate target in `make/core.mk`; `make/storage.mk` declares `conf: $(S3_JSON)` and
a file rule that renders `s3.json` via `envsubst` with an explicit variable list, re-rendering only
when the template or `.env` changes. `make up` starts the stack (only `compose.storage.yaml`
exists, so only SeaweedFS starts).

## Deviations from the tutorial
What differed, why, and the error that forced it.

1. **`SCALE` in the Makefile now checks that the Spark stack file exists.** Tutorial 0's Makefile
   stub added `--scale spark-worker=$(SPARK_WORKERS)` whenever `spark` appeared in `STACKS` — and
   the default `CORE` list contains `spark`. This phase's tutorial says `make up` "only adds the
   worker-scaling flag once the Spark stack exists", but `make up` failed with
   `no such service: spark-worker: not found` (reproduced via
   `./dc up -d --scale spark-worker=2 --dry-run`). Fixed by guarding the flag with
   `$(wildcard platform/compose.spark.yaml)`, the smallest change that implements the tutorial's
   stated behaviour; Phase 2 needs no further Makefile change.
2. **Target placement.** The tutorial says "Add to the `Makefile`" for `conf`/`buckets`/`s3`; per
   tutorial 0's convention ("targets go in that stack's `.mk` file"), `buckets` and `s3` live in the
   new `make/storage.mk` and the `conf` render replaced the placeholder in `make/core.mk` (which
   `make up` already depends on). No behaviour change.
3. **Owner-directed plan edit squashed into the phase commit — then removed after review.** The
   owner edited tutorial 2 (new last bullet under Phase 11 Explore: a future refactor to make
   `conf` pluggable per stack) and asked for it to land inside this phase's single commit, so the
   branch was amended and pushed with `git push --force-with-lease` — normally an owner-only,
   destructive action, done here on the owner's explicit instruction. A stray deletion of the
   tutorial 2 title/byline in the same edit was spotted during review and restored (fixed by the
   owner) before committing.
4. **Review fix (PR #2): `conf` made pluggable per stack in this release.** The owner's inline
   review asked to implement the refactor now ("Fix this in this release itself, refactors are
   costly"), then remove the explore task. Done: `conf` is recipe-less in `make/core.mk` (plus
   `.PHONY: conf`), and `make/storage.mk` owns the render — `conf: $(S3_JSON)`, prerequisites =
   template + `.env`, recipe runs `envsubst` with an explicit variable list. The explore bullet was
   removed from tutorial 2 (file identical to `main` again); a stream stack later adds
   `conf: <file>` in `stream.mk` the same way. Amended into the same single phase commit and
   force-pushed with `--force-with-lease` per the review instruction.

## Findings
Anything worth remembering: surprises, measurements, ideas for later.

- **SeaweedFS 4.51 `mini` confirmed against the image, not just docs:** `-s3.config` exists; master
  http defaults to 9333 (so `weed shell -master=localhost:9333` works); S3 defaults to 8333; there
  is an `-s3.port.iceberg` flag for the built-in Iceberg REST catalog (the tutorial's 8181).
  Container listens internally on 7333, 8080, 8888 (filer), 9333 (master), 18080, 18888, 19333 —
  only 8333 is published to the host.
- `mini` has a `-bucket` flag (falls back to `S3_BUCKET` env) that pre-creates buckets at startup —
  an alternative to the `weed shell` loop in `make buckets`. Kept the tutorial's approach.
- **`make s3` echoes the credentials** (make recipe echo) into the terminal. Harmless now — `.env`
  still holds the `change-me` placeholders — but once the owner sets real S3 secrets they will
  appear in shell output/logs. Phase 10 hardening candidate (silence/mask the recipe).
- `.env` secrets are still placeholders; the endpoint works because `s3.json` is rendered from the
  same values. Rotating to real keys later needs only: edit `.env`, `make conf`, restart the stack.
- The `amazon/aws-cli:2.39.2` image is pulled lazily on the first `make s3` (tag pinned in
  `versions.env`, verified in t0).
- Data lands in `/lake/lakehouse/seaweedfs` on the ZFS `lake` pool as intended; the compose
  interpolation resolves everything from `versions.env` + `.env` via `./dc`.
